# P2 实施计划

日期：2026-10-16（Asia/Shanghai）。负责人已确认按阶段实施，机器人聊天的所有费用暂不作为约束。

本文定稿文件职责、配置契约、预算和数据迁移，不代替当前运行契约。当前已交付前三阶段，生产默认启用规则轮次聚合与正文接入；MODEL 时机判断和多成员权威历史仍待后续阶段。当前运行方式仍见 [接口文档](接口文档.md)，需求及测试矩阵见 [P2 任务文档](P2任务文档.md)。

## 一、范围与规则

- 保持 active 一对一 USER 文本、单活动进程、快速 HTTP 200、PostgreSQL 权威存储和 Redis 原有缓存/锁/限流用途。
- 不新增依赖、中间件、HTTP 接口、自动 Push、分钟级等待或重启续发。
- 当前即时流程中 Reply Token 仅以隔离内存引用短暂持有；不放入成员业务快照、数据库、Redis、日志、模型和对象打印，终结或替换释放引用。
- 生成成功、LINE 接受、业务事务提交分别确认；UNKNOWN 不补发，不因缓存或持久化失败重新消费。
- 技术提示继续默认静默，规则回退决定正常生成时机，不意味着开启技术提示。
- 不设金额上限、不为节约费用更换模型；输入、输出、时间、调用次数与容量仍有限，实际用量只作观测。
- 前两阶段不修改运行中的 application.yml、环境示例或生产 Bean 装配；新配置及轮次模式只有后续显式装配后才生效。

根规则已补齐 aggregation/decision 的职责和依赖方向、P2 多成员约束及费用取舍。P1 保留单成员历史定义，并澄清短时内存凭证与当前静默规则。

## 三、配置契约与装配计划

以下是类型契约及环境变量映射。第三阶段已装配全部聚合变量、RULE 模式与技术提示冷却，生产默认开启；策略模型/熔断变量仍是第六阶段目标，实际运行默认及已实现范围以接口文档 2.6 为准。

### 聚合：line.ai.aggregation

| 属性 | 未来环境变量 | 契约默认值 |
| --- | --- | --- |
| collection-span | AI_AGGREGATION_COLLECTION_SPAN | 6s |
| queue-reserve | AI_AGGREGATION_QUEUE_RESERVE | 3s |
| dependency-reserve | AI_AGGREGATION_DEPENDENCY_RESERVE | 1s |
| generation-reserve | AI_AGGREGATION_GENERATION_RESERVE | 32s |
| rule-wait | AI_AGGREGATION_RULE_WAIT | 1s，每轮最多一次规则等待 |
| max-members | AI_AGGREGATION_MAX_MEMBERS | 8 |
| max-characters | AI_AGGREGATION_MAX_CHARACTERS | 4096 UTF-16 单元 |
| max-buffered-members | AI_AGGREGATION_MAX_BUFFERED_MEMBERS | 2048，包含仍被快照保留的成员 |
| max-buffered-characters | AI_AGGREGATION_MAX_BUFFERED_CHARACTERS | 2000000 UTF-16 单元 |
| max-regenerations | AI_AGGREGATION_MAX_REGENERATIONS | 1，允许 0..1 |
| max-generation-attempts | AI_AGGREGATION_MAX_GENERATION_ATTEMPTS | 2，允许 1..2；重试与重生成共享 |

时长须大于零且不超过整体最大 50s 的边界；规则等待不得大于配置收集跨度。单轮容量须能装入全局容量；一次重生成至少需要两次物理请求额度。正文生成预留用于规划收集窗口，并非保证正文一定完成或必须占用 32 秒。

会话上限、待执行作业上限与全局模型在途继续复用现有 AiProperties 的 max-users=1024、queue-capacity=256、workers=4，装配阶段再验证策略子并发不超过共享总额度。每用户固定最多一个活动轮次和一个待处理轮次，旧 user-queue-capacity=3 不解释为三轮；接入时同步说明旧属性的兼容处理。

### 判断：line.ai.decision

| 属性 | 未来环境变量 | 契约默认值 |
| --- | --- | --- |
| mode | AI_DECISION_MODE | 最终目标 MODEL；第三阶段实际运行默认 RULE，MODEL 未实现并快速失败，规则不调用时机模型 |

| max-concurrent | AI_DECISION_MAX_CONCURRENT | 1，使用全局模型总在途额度的子额度 |
| max-input-tokens | AI_DECISION_MAX_INPUT_TOKENS | 4096，保守输入预算，不声称精确计费量 |

冷却时间必须为正且能转换为纳秒；策略调用最多两次，正文最多两次。放宽 token 配置不解除调用、时限、资源及发送边界。提示冷却表复用会话用户容量约束，满时保守抑制提示，并过期清理。

## 四、预算与状态衔接

```text
D_turn = min(首条入口截止, 所有已准入成员入口截止)
C_turn = min(首条接收 + collection-span,
             D_turn - queue-reserve - dependency-reserve - generation-reserve - send-reserve)
D_generation = min(D_turn - send-reserve, 首次正文开始 + model.total-timeout)
```

- 总入口默认 45s、上限 50s，发送预留默认 3s；收集 6 + 排队 3 + 协调 1 + 正文 32 + 发送 3 = 45s。
- 从 HTTP 原始接收时间计时；首条到协调器已耗时 4s 时，默认收集只剩 2s，不能再等完整 6s。
- 规划预留不足时收集压缩为零；正文只能使用总预算减发送预留后的实际余量，不能制造额外时间。
- TurnBudget 是不可变纯计算对象；including 只能收紧已有截止，beginGeneration 第一次冻结正文截止，后续调用不延期。状态所有者必须保存返回的新对象，不得在晋升/重生成时另建初始预算。
- 当前对象不实现状态机、线程调度、调用次数记账、模型取消、凭证选择或发送权；这些在后续阶段接入并分别测试。
- 状态锁内禁止网络/数据库 I/O；控制事件使用有界合并或预留槽，不被普通消息满载丢弃。等待不占模型线程、不创建每用户线程。
- 物理调用取消后，在实际本地传输/清理未结束前继续占资源；迟到结果必须核对 epoch、turn_id、input_version 与 generation_version。
- 删除等待沿用 60s、墓碑 75s；Redis 锁覆盖实际剩余流程和提交余量，停机按统一截止收尾，不靠新消息延长 TTL 获得额外轮次预算。

### 第二阶段执行基础（组件已实现，第三阶段已接入生产）

- `InboundMember` 保存完整文本、事件/消息标识、原始时间/序号与成员各自 trace；`TurnSnapshot` 是作用域内不可修改的有序快照，不含凭证、SDK 对象或未发送 assistant 草稿。
- `TurnBuffer` 对活动/待处理成员及在途快照统一计数，共享原文不重复计字符；关闭轮次不提前释放仍在执行的快照。字符数按 UTF-16 原文计算，不等于 JVM 内存占用。借用快照不能在工作结束后继续持有。
- `SessionScheduler.enableTurns` 只允许在空闲时一次性互斥切换；切换后逐条 submit 明确拒绝，沿用原工作池、定时池、取消及停机入口。没有另一个同时运行的会话服务；第三阶段已由 AggregatedChatFlow 在启动时调用切换入口。
- `TurnCoordinator` 是轮次模式唯一状态所有者，每用户最多一活动一待处理；按接收序号准入，冻结的待处理轮次不收第三轮。定时引用每轮最多三个，取消后移除，迟到唤醒核对版本。
- 语义 WAIT 不消耗工作线程，不套用旧 3s 等待上限；READY 执行排队最多等待原 queue-wait，输入变更和晋升不重置起点。正文优先于策略，其他 READY 用户按队列顺序轮转；策略子并发不超过共享执行额度。
- 每次调用绑定会话代次、轮次、输入/正文版本和调用序号；同一建议只能应用一次。新输入使旧判断失效，不逐片并发判断；模型判断最多两次，规则等待最多一次，收集截止强制推进。
- 正文重生成最多一次，旧执行实际退出前不启动新执行；重试必须通过 reserveGenerationRetry 消耗同一轮剩余请求额度，不能与重生成各拿两次。第三阶段模型适配已接入该额度接口；P1 兼容模式保留原单次生成内重试。
- 版本核对与进入 SENDING 在同一控制锁内完成；SENDING 后新输入进入下一轮。已接受、明确失败或 UNKNOWN 只应用一次，执行退出但未报告发送结果时收尾为 UNKNOWN，不能追加提示或再次发送。
- 控制锁外运行工作、请求中断和发布完成通知；取消已经开始的工作仍占在途及缓冲资源，直到 TurnWork 返回并关闭快照。尚未实际开始的排队作业可原子取消并归还预占资源，迟到执行不能重复归还。
- SessionScheduler 已接入 UserDataPurger；删除守卫先取消，统一屏障在事务外等待，purge 若仍有该用户轮次会明确失败，不在事务内等待。第三阶段已接入并测试 UserWorkTracker 实际工作登记；真实 SDK 传输取消语义仍待后续验证。
- 已准入轮次的业务终态通过正常完成的 TurnResult 发布，保留固定原因；不抛出业务失败去释放上游去重。新工作失败、时机回退和终态的正式日志事件仍由后续编排接入，第二阶段没有新增生产日志，第三阶段已增加正式轮次日志及原指标接入，不新增用户标签。

第二阶段结论来自可控时钟/模拟 TurnWork 及真实线程组件测试；第三阶段另增加实际入口的临时存储、模型替身与本地 LINE SDK 测试，覆盖连发、未知重投递及删除。真实策略模型、远端 LINE 及后续阶段的完整竞态矩阵仍未验证。

### 迁移、写入与回退

1. P1 迁移只选择 USER 同会话、TEXT、非空原文/消息标识/关联/接收边界、恰好一条匹配入站与一条正常 AI 出站的合法记录。重复、歧义、缺失或未知来源全部原样保留并排除；不使用相邻行猜测，不删旧消息。
2. 旧行的轮次标识由迁移一次生成并持久化；历史 trace_id 不凭空补造。新轮次与发送标识由会话所有者生成并保持稳定，重复落库不能新增第二轮或第二出站。
3. 新成功出站、轮次和成员在同一异步业务事务提交；原始入站仍逐条尽力落库。关联前可依据冻结的允许业务快照幂等补齐缺失入站；遇到已存在但用户、来源或内容不匹配的行，事务失败，不覆盖原始记录。
4. 事务失败整体回滚；发送已经发生，不能用重发修复记录。技术提示、FAILED、UNKNOWN、撤销输出不生成正常成功历史。
5. Redis 历史使用 context-v2 命名空间，旧 context 不当作新格式解析；新 key 未命中从 PostgreSQL 回源，旧 key 依原 TTL 淘汰。删除覆盖 context/context-v2/rate、本地快照、轮次状态与冷却，锁仍由所有者安全释放。
6. last_chat_gap 以本轮首条 received_at/sequence 为查询边界，排除全体当前成员和下一轮，保留首次与读取故障区别。未落库的上一轮用有界已接受内存快照衔接，不依赖重复发送。
7. 发布前停旧实例并备份；大数据量先在离线副本测量迁移锁、耗时与磁盘需求。迁移失败应停止启动，不跳过或修改已应用脚本。P2 新格式开始写入后，不直接回退旧 P1 二进制读取多成员历史；回退需单独验证前向修复方案。

生命周期第七阶段另新增迁移保存同事件时间时的接收排序边界；不把新增列塞回已应用的 V4。关注状态优先比较 LINE 事件时间；同时间以本服务已确认接收时间/顺序决定，数据库和内存使用同一比较规则，重复事件不再次更新。迁移前没有排序信息的旧同时间状态采取保守保持，避免旧取消关注取消重新关注后的会话；不宣称还原设备原始顺序。

## 六、SDK 核实与调用边界

已核对 [OpenAI Java 文档](https://developers.openai.com/api/reference/java)、[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs) 和本地官方发布的 openai-java-core 4.81.0 源码：Responses 的 ResponseCreateParams.text、ResponseTextConfig.format 与 ResponseFormatTextJsonSchemaConfig.schema/strict 可表达严格结构化输出。不能仅复制最新版文档中的便利方法而假定锁定版本也存在。

当前 GenerationConfig 显式 maxRetries(0)、LogLevel.OFF；后续策略同样关闭自动重试和 HTTP 信封日志。结构化输出字段定为 action、wait_ms、reason_code；action 仅 REPLY_NOW/WAIT_FOR_MORE，reason_code 仅 COMPLETE_INPUT/POSSIBLE_CONTINUATION/USER_REQUESTED_WAIT/URGENT。NOW 的 wait_ms 必须为 0，WAIT 必须为当前允许范围内的正整数；额外字段、未知枚举、非整数、拒绝、空白或未完成响应都回退规则，不要求自由文本推理。

已核对 [LINE Reply 约束](https://developers.line.biz/en/reference/messaging-api/nojs/#send-reply-message)：一次使用、尽快发送；一分钟和本地 45s 不是送达保证。第四阶段用锁定 LINE SDK 10.2.0 与本地 Stub 验证明确失败和 UNKNOWN；取消 Future 不等于远端未执行，不能自动补发。

真实 SDK 的取消是否及时结束传输及是否仍有在途回调，要在第六阶段本地 HTTP Stub 中验证；第一阶段的数学预算测试不能替代该验证。全部自动测试禁止真实模型/LINE 调用。

## 七、验收与剩余验证

- 第一阶段：配置绑定、无效配置、时间压缩、成员收紧、生成截止复用、发送预留与原始入口年龄；验证现有全量回归。
- 后续自动验收：P2 任务文档必测矩阵全部通过，特别是一轮最多一次 Reply、成员去重、UNKNOWN 不重启、并发删除、原文完整和凭证禁记。不能把第一阶段预算对象通过等同于这些场景已实现。
- 人工对照：相同虚构轨迹分别跑 RULE/MODEL，记录提前接话、语义段拆轮、撤销、P50/P95、放弃/未知及 1～5 分的接话适当性/连贯性/相关性；逐条复核不合理结果。第一阶段不设未经真实测试支撑的模型质量保证。
- 资源压测：记录在途模型、定时、待执行、缓冲成员与字符水位；达到配置上限应有界拒绝，公平性与内存实占另测。
- 真实模型的 2s 时机判断适配、正文延迟、LINE 收件与人工质量尚未验证；真实费用不是验收门槛，取消或未知用量不得伪造零消耗。
