# 数据库设计

本文维护表结构、索引及数据治理设计。配置默认值与运行步骤统一以 [接口文档](接口文档.md) 为准。

当前交付：P0、P1 与 P2 前五阶段，包含单实例聚合与完整已接受轮次。PostgreSQL 是唯一持久化权威来源，Redis 仅提供可丢弃热缓存、所有权锁和限流；存储由部署方提供。

## 版本与连接

目标与测试版本为 PostgreSQL 18.6，测试镜像在 `pom.xml` 的 `postgresql.image` 集中管理。
受支持版本以 [PostgreSQL 官方列表](https://www.postgresql.org/support/versioning/) 为准。
Flyway 使用 11.15.0：已核对该版本 PostgreSQL 模块官方发布源码，支持主版本 18；
该版本 [官方源码包](https://repo.maven.apache.org/maven2/org/flywaydb/flyway-database-postgresql/11.15.0/flyway-database-postgresql-11.15.0-sources.jar)
中的 `PostgreSQLDatabase.ensureSupported` 使用主版本 18 作为兼容边界。

数据库由部署方提供。地址、账号、密码仅通过 `DATABASE_URL`、`DATABASE_USERNAME`、`DATABASE_PASSWORD` 注入，
不得写入仓库或运行日志，缺失时启动快速失败。HikariCP 业务连接池默认最多 8 个连接，获取连接超时 3000ms。
不允许生产配置启用数据库配置 DEBUG 日志。Flyway 地址日志和 Hikari 配置日志已关闭。

event_log 索引：ts、trace_id、(user_id, ts)、(event, ts)。
audit_log 索引：created_at、trace_id、(target_user_id, created_at)。
两表不关联用户外键，取消关注保留记录；本次手动删除的操作证据也能在用户删除后写入。
完整虚构行见 [event_log](examples/webhook/event-log.json)、[audit_log](examples/push/audit-log.json)。

事件与审计使用 line-log 独立 Hikari 池，复用外部数据库连接配置；业务连接池保持独立。
事件/审计正常写入与保留清理只用日志池；Flyway 和显式的跨存储用户删除事务使用业务池。
日志池启动不等待可用连接，写入失败经一次重试后降级 stdout；不会占用业务池等待连接。
该隔离不能隔离同一个 PostgreSQL 服务器整体故障，也不提供可靠消息队列。

## 记录与失败处理

消息 Handler 将入站提交到独立有界持久化线程池，继续执行原有回复流程，成功回复后再提交出站记录。
所有 SDK 可解析消息均保存业务元数据；standby 保存入站、不发送、不保存出站。
缺少用户来源时跳过存储，不伪造用户标识。文本保持完整，不进行 HMAC 或其他脱敏。
SDK 的 replyToken、quoteToken、markAsReadToken 及嵌套凭证字段在队列提交前排除，原事件不进入数据库队列。

持久化默认 2 个线程、512 个排队任务。失败与拒绝输出 `persist.failed` 并增加指标，
不改变 Webhook HTTP 200、不阻塞或阻止即时 Reply。队列拒绝不会回退到调用线程执行。
这是一种尽力记录：队列满、进程崩溃或停机等待超过 30 秒时可能丢记录，不提供持久化队列保障。
入站幂等索引只避免重复存储，不能替代 Webhook 事件去重，也不能避免再次回复。
Webhook 与持久化线程池共用 MdcTaskDecorator，落库失败保留原请求 trace_id、事件 ID 和完整 user_id。
日志只输出异常类型与调用帧，不输出 JDBC 异常消息、SQL 绑定参数或数据库连接值。

## 历史查询

`ChatHistoryService.findRecent(userId, limit)` 返回最新 N 条消息的时间正序，不开放新的 HTTP 接口。
同时间以 id 稳定排序。limit 范围为 1..`line.chat.history-max-limit`（默认 100），无记录返回空列表。
查询数据库失败会明确抛出 DataAccessException，调用者决定后续降级策略。

## 保留与删除

取消关注只更新状态，保留全部数据；重新关注恢复状态，不安排任何自动删除。
聊天清理 `CHAT_CLEANUP_ENABLED=false` 默认关闭；启用后按 `CHAT_RETENTION_DAYS=90` 清理。
每小时触发一次，每次最多删除 `line.persistence.cleanup-batch-size=500` 条；仅删除严格早于截止时间的数据。
每次调度一个短事务批次，积压可通过缩短间隔或调大批次处理。

`UserDataDeletionService.deleteAll(userId)` 是显式手动调用的 Java 入口，不开放删除 HTTP 接口。
它在一个业务数据库事务中调用全部已注册的 `UserDataPurger`，当前覆盖 chat、user、event_log、历史 audit_log 及 Redis/本地 AI 状态；任一删除失败回滚全部数据库修改。
事务提交后新建 user.data.deleted 的 SUCCESS 事件/审计；回滚后记录 FAILED，不谎报删除成功。
本次删除审计保留完整目标用户作为操作证据；重复调用仍可安全执行并记录本次操作。
后续新增用户数据存储只需实现 `UserDataPurger` 并注册为 Spring Bean。
Redis 不受 PostgreSQL 本地事务保障；失败可以幂等重试，但不能承诺数据库回滚恢复已删除 Redis 缓存。
P1 已实现 UserWorkTracker 屏障：事务外阻止新工作、取消等待 AI，最多等 60 秒排空在途生成/发送（含手动 Push）和异步写入，失败明确返回；成功后旧请求禁止重新写回，新请求可重建历史。

P2 第二阶段已给 SessionScheduler 增加 UserDataPurger 扩展点：显式启用轮次模式后，删除守卫取消未发送工作，排空后状态自动回收；purge 检测到该用户仍有轮次或在途执行时立即失败，不在事务中等待或假报成功。当前生产未启用轮次模式，仍为 P1；新流程的完整屏障接入与轮次/成员表迁移待后续阶段验证，详见 P2 实施计划。本轮没有新增表或迁移脚本。

### UserDataPurger 扩展方式

1. 新增用户数据存储时，在所属业务包实现 `UserDataPurger.purge(userId)` 并注册 Spring Bean，构造器注入所需 Repository；统一删除入口自动收集，无需修改其调用列表。
2. 删除按完整 user_id 定位，应幂等：没有数据或重复调用时安全返回。PostgreSQL 删除复用当前业务事务，失败抛出明确异常，不吞异常后假报成功。
3. 新存储位于 common 时，在 user 或所属业务包提供适配器，方向为业务包 → common，不能让 common 反向依赖 UserDataPurger。现有 LogDataPurger 即采用该方式。
4. 新增测试验证统一入口确实清除新存储、重复删除安全、数据库故障回滚，以及审计提交/失败结果；不能只测试删除器自身而遗漏统一入口。
5. 后续 Redis 等外部存储不参与 PostgreSQL 本地事务，需自行设计可重试的删除与补偿；TTL 不能替代显式用户删除。P1 RedisConversationMemory 已接入统一删除，原子拒绝仍有锁的清理；不抢占其他持有者，失败可以重试。

运行时 stdout 与本地易读文件不属于按用户删除的数据库表，不由 UserDataPurger 修改；本地文件仍由部署方手动管理。

事件与审计保留策略互相独立，默认关闭；显式启用后保留天数分别默认为 30/180，
每次调度按共用的清理批大小上限清理，首次延迟与后续间隔各自配置。具体配置统一见接口文档。

## 存储边界与后续能力

- Redis 热缓存、锁、限流已接入，所有 key 有 TTL；共享事件去重、跨实例排序与删除协调尚未实现。

| 存储 | 职责与状态 | 丢失后的影响 |
| --- | --- | --- |
| PostgreSQL | 已实现；用户、对话、event_log、audit_log 的权威持久化来源 | 需要数据库备份/恢复，由部署方保障 |
| 内存队列/去重缓存 | 已实现；有界异步缓冲与单实例去重 | 重启丢失，不能作为可靠持久化或多实例幂等保障 |

## P1 会话迁移与历史

V3 仅新增字段和索引，不重写或删除原消息；旧记录保留 UNKNOWN/LEGACY，不猜测来源或配对。部署按先停旧单实例再启动新实例执行，Flyway 自动迁移。

| chat_message 新字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| source_type | TEXT NOT NULL，默认 UNKNOWN | USER/GROUP/ROOM/UNKNOWN，按实际来源写入 |
| conversation_id | TEXT，可空 | 私聊 userId、群 groupId 或 roomId |
| reply_kind | TEXT NOT NULL，默认 LEGACY，固定枚举检查 | AI/FALLBACK/BUSY/RATE_LIMITED/SERVICE_UNAVAILABLE/INPUT_TOO_LONG/LEGACY |
| in_reply_to_message_id | TEXT，可空 | 正常出站与提示关联本次入站，不根据相邻行猜测 |
| correlation_id | TEXT，可空 | 当前 webhookEventId，双方需相同 |
| received_at | timestamptz，可空 | 服务接收排序边界，与旧 created_at 事件时间分离 |
| received_sequence | bigint，可空 | 单实例有序入口的单调事件序号 |

私聊历史索引 `(user_id, received_at DESC, received_sequence DESC)`（source_type=USER）；配对索引 `(user_id, in_reply_to_message_id, correlation_id)`（OUTBOUND/AI）。同批共享接收时间但序号严格递增；接收时间按 PostgreSQL 微秒精度保存。数据库没有伪造旧来源/序号，进程重启的序号只在接收时间相同的边界有意义，单实例升级不得并行运行。

`ChatHistoryService.findPrivate` 从 ai_turn/ai_turn_member 查询完整已接受轮次，默认消息预算 200 条，每轮按全部成员加一条回复计数，整轮取舍；按本轮首条 received_at/sequence 截止并排除全部当前/未来成员，只纳入同用户私聊 TEXT 与明确关联且已接受的 AI 文本回复。提示、未发送、非文本、LEGACY/UNKNOWN 不进入上下文。窗口内配对不足返回较少轮次，不无限扫描；Redis 最终最多取 10 轮。`lastPrivateInbound` 另查最近一条边界之前的私聊入站，包含非文本；本地有界时间观察连接异步写库延迟，并按接收边界选择上一条，不以事件时间大小判断先后。

## Redis key 与本地状态（P2 第五阶段）

| key | 用途 | TTL | 丢失影响 |
| --- | --- | --- | --- |
| `AI_NAMESPACE:{userId}:context-v2` | JSON 正常已确认完整多成员轮次，最多 10 轮 | 每次写入后 7d，可配置 | 回源 PostgreSQL 的已持久化轮次；未持久化记录可能缺失 |
| `AI_NAMESPACE:{userId}:lock` | 随机唯一持有者保护发送/提交；Lua 原子校验释放和保存 | 获取时剩余总预算+1s | 持有权丢失禁止发送/提交；不保证跨服务远端原子副作用 |
| `AI_NAMESPACE:{userId}:rate` | Lua 原子 INCR 与首次 PEXPIRE，默认 12 次/60s | 首次计数后 60s，可配置 | 计数重置可接受，不持久化恢复 |

Redis 测试镜像在 pom.xml 集中管理；生产通过 REDIS_HOST/PORT/USERNAME/PASSWORD/SSL 注入，不自动启动 Redis。命名空间应用/Channel 唯一，完整 userId 不脱敏。缓存 TTL 不删除 PostgreSQL，所有聊天/日志清理开关仍默认关闭。

本地已确认轮次快照和入站时间观察最多 1024 用户，每用户最多 10 轮/200 个时间观察，写入触碰更新 7d 读取失效时间，容量满淘汰旧用户；全局等待 256。工作跟踪最多 4096 用户，空闲状态自动移除，删除成功留 75s 墓碑阻止旧入口任务。P2 每用户最多一活动轮次和一待处理轮次；关闭聚合才沿用 P1 单条排队。统一删除清除此用户 Redis context/context-v2/rate、本地快照/观察、排队任务；锁只能由其所有者释放，发现仍有锁则删除失败。

依赖查询通过独立有界线程池等待最多 500ms，取消迟到结果；驱动未响应取消时占用的实际工作仍计入删除屏障，屏障超时明确失败，不假报排空。尽力异步落库、缓存失效与重启不能恢复尚未持久化的数据。


## P2 第三/四阶段过渡记录与第五阶段升级

第三/四阶段多成员成功出站的 content.ai_turn 保存完整有序业务成员，in_reply_to_message_id=null。第五阶段 V4 仅在全部原成员的用户/会话、消息/事件标识、完整原文、时间和接收顺序均匹配且归属唯一时建立权威关联；保留原 turn_id、成员 trace 和原始 JSON。缺失、畸形、重复或歧义记录不删、不强行迁移，也不进入模型历史。

TurnReplyService 的技术提示冷却仅为有界可丢弃内存，最多 AI_MAX_USERS 条，过期清理；已接入 UserDataPurger。SessionScheduler 在删除工作排空前拒绝 purge，成员工作计数直到真实执行及清理退出才释放，取消不假报排空。正文、真实发送分类与后续生命周期验证范围见接口文档 2.6。


## P2 第五阶段成功轮次（V4，已实现）

| 表 | 主键与主要业务字段 | 约束 |
| --- | --- | --- |
| ai_turn | turn_id UUID；send_attempt_id UUID；user_id/conversation_id；outbound_message_id；first_received_at/sequence；accepted_at；member_count | 发送标识及出站唯一；会话等于用户；成员数与序号为正；固定 OUTBOUND/TEXT 组合外键 |
| ai_turn_member | turn_id、member_order；inbound_message_id；user_id/conversation_id；webhook_event_id；trace_id | 轮次内顺序主键；同会话入站唯一归属；固定 INBOUND/TEXT 组合外键；成员与轮次范围一致；旧迁移 trace 可空 |

chat_message 增加 id/user_id/conversation_id/direction/message_type 组合唯一键。轮次出站删除级联轮次，轮次删除级联全部成员；入站删除级联对应成员。索引覆盖轮次用户/会话/首条接收边界、accepted_at 以及成员 inbound_message_id。查询验证数量和连续顺序、来源/关联及全部成员边界，排除残缺轮次；聊天保留清理在同一事务内按既有批次上限删除旧消息并另回收一批残缺轮次，不删除其尚未过期的剩余原始消息。

ChatTurnService 在原 AsyncPersistence 有界业务队列中执行一笔 PostgreSQL 事务：依据完整允许业务快照补缺入站、核对已有消息，再插入唯一已接受正常出站、轮次及所有成员。任一冲突全部回滚，不覆盖已有原文。会话所有者生成稳定 turn_id/send_attempt_id，按固定顺序取得对应事务锁，重复提交校验同一业务快照后直接返回，不增加第二条出站。用户手动删除通过 ChatTurnService 的 UserDataPurger 与消息级联双重覆盖新表，仍由统一删除服务控制事务和在途屏障。

成功历史与技术提示分离；FAILED/UNKNOWN/撤销输出不写成功轮次。P1 单条兼容模式也通过相同成功事务保存。模型输入按每轮全部 user 成员和唯一 assistant 展开，预算只能删除完整旧轮。Redis context-v2 保存该结构，旧 context 仅按原 TTL 自然失效，不解析为新结构；显式删除同时清除两代 key。LINE 接受后先保留本地有界轮次，再尝试 Redis 更新，衔接落库延迟；断电或缓存丢失只能恢复已提交数据，不能由孤立入站补发。

V4 还只迁移唯一匹配的合法 P1 正常轮，来源未知、提示、关联缺失或歧义数据原样保留；历史 trace 不编造。既有 V1/V2/V3 未改写。部署前停旧实例并备份，大数据量需在离线副本评估迁移锁、时间和空间；新结构开始写入后不能直接退回旧二进制。自动测试已在临时 PostgreSQL 执行 V3→V4、重复启动、部分/畸形过渡数据及关系约束，不代表已迁移生产数据。
