# 三、步骤 1：数据持久化

## 1.1 表结构（Flyway 迁移脚本创建）

**line_user**

- user_id（主键，LINE userId）
- status（FOLLOWING / UNFOLLOWED）
- followed_at、unfollowed_at、created_at、updated_at

**chat_message**

- id（主键）、user_id（索引）
- direction（INBOUND / OUTBOUND）
- line_message_id（入站消息建唯一索引，作为幂等兜底，出站可为空）
- message_type（TEXT / IMAGE / STICKER 等）
- content（文本内容；非文本类型只存元数据；**不存二进制内容**）
- model_name、input_tokens、output_tokens、latency_ms（出站消息使用，当前阶段允许为空）
- created_at；联合索引 (user_id, created_at)

## 1.2 落库规则

2. Follow / Unfollow 事件更新 line_user（用户重新关注时更新状态而不是报错）
4. 收到文本消息入库；出站消息通过 `ChatMessageService.recordOutbound(...)` 提供给后续模块调用（当前 echo 回复成功后也要记录）
6. **落库必须异步**，不得阻塞回复；失败只记日志与指标，**不得导致 Webhook 重试或影响用户收到回复**
8. 入站消息利用唯一索引做幂等兜底，重复写入被安全忽略
10. 禁止存储：replyToken、quoteToken、Channel Secret、Access Token、任何 API Key

## 1.3 历史查询能力

提供 `ChatHistoryService.findRecent(userId, limit)`，返回按时间排序的最近若干条消息，供后续 AI 模块构建上下文使用。本阶段只实现并测试该能力，不接入 AI。

## 1.4 数据治理

2. 消息清理开关独立配置，默认关闭；启用后按保留天数（默认 90 天）定时分批清理，单批大小可配置，避免长事务

4. 定义 `UserDataPurger` 接口（放 user 包）：`purge(userId)`，用于"删除某用户全部数据"。

   - chat、user 各自实现并删除数据库中的数据
   - 提供统一入口 `UserDataDeletionService.deleteAll(userId)`，调用所有已注册的 UserDataPurger，并写入审计（见步骤 3）
   - 后续的 AI 模块（Redis 上下文等）只需新增一个实现，不改本阶段代码

6. 已确认：取消关注仅更新状态，保留全部用户数据；重新关注恢复状态；不因取消关注自动删除，由用户后续手动处理

# 四、步骤 2：结构化日志

## 2.1 日志格式

2. 所有环境 stdout：JSON 单行输出；本地开发 profile 可额外保存易读日志文件，该文件不提交 Git
4. 先确认当前 Spring Boot 版本是否内置结构化日志（`logging.structured.format`），**优先使用内置能力**；若需新增依赖，先说明理由
6. 固定字段（每条都有）：ts、level、service、env、version、instance、trace_id、event
8. 按需字段：webhook_event_id、user_id、outcome、duration_ms、http_status、error_type、message_type、model、input_tokens、output_tokens
10. service、env、version、instance 从配置/环境变量读取

## 2.2 链路追踪

2. 在 Webhook 入口生成 trace_id，写入 MDC，请求结束时清理；响应头返回 trace_id 便于排查
4. 为现有异步线程池配置 TaskDecorator，保证 trace_id、webhook_event_id、user_id 在异步线程中保留
6. 落库、LINE 发送等所有异步路径都必须携带 trace_id

## 2.3 完整用户数据记录（已确认覆盖原脱敏规则）

2. 日志、event_log、audit_log 和业务表允许保存完整 userId 与消息原文，不进行 HMAC 或其他脱敏。
4. 不要求 LOG_USER_REF_KEY；统一使用 user_id，审计目标字段使用 target_user_id。
6. 仍禁止记录密钥、各类 Token、签名与数据库密码；不得直接保存包含凭证的原始请求头或完整 Webhook 请求体。
## 2.4 事件名规范

在 `LogEvents` 中以常量集中定义事件名，日志与事件记录必须引用常量，新增事件需先登记。
**以下事件一次性登记完毕**（标注"后续"的事件本阶段只登记常量，由后续阶段使用）：

- 用户行为：`user.follow`、`user.unfollow`、`user.message.received`、`user.postback`、`user.rate_limited`（后续）
- Webhook：`webhook.received`、`webhook.signature_invalid`、`webhook.duplicate`
- AI：`ai.generate.success`（后续）、`ai.generate.failed`（后续）、`ai.fallback.used`（后续）
- LINE 出站：`line.reply.sent`、`line.reply.failed`、`line.push.sent`、`line.push.failed`、`line.retry`
- 基础设施：`memory.cache_miss`（后续）、`lock.timeout`（后续）、`executor.rejected`、`persist.failed`
- 审计：`internal.push.invoked`、`user.data.deleted`

`user.message.received` 记录 message_type、文本长度与完整业务内容；凭证字段必须排除。

## 2.5 级别约定

ERROR = 需要人介入；WARN = 已被处理但值得关注（重试、兜底、限流）；INFO = 关键业务事件；DEBUG = 默认关闭，生产禁止长期开启。

# 五、步骤 3：事件落库、审计、指标

## 3.1 event_log 表与 EventRecorder

**event_log 表字段**：id、ts、event、level、trace_id、webhook_event_id、user_id、outcome（SUCCESS / FAILED / SKIPPED）、duration_ms、http_status、error_type、message_type、model、input_tokens、output_tokens、detail（jsonb）、service、env、version、instance
**索引**：ts、trace_id、(user_id, ts)、(event, ts)

**EventRecorder 要求**（放 `common.logging`）：

2. 只记录 `LogEvents` 中登记的事件
4. **异步**：有界内存队列（容量可配置）+ 后台线程批量写入（批大小、刷新间隔可配置）
6. 使用**独立的 DataSource 与小连接池**（大小可配置，默认 2~3），不得占用业务连接池
8. 队列满时**丢弃并累加指标 `log.dropped`，绝不阻塞调用线程**
10. 写入失败重试 1 次；仍失败则把该事件以 JSON 输出到 stdout 并产生 `persist.failed`。**`persist.failed` 本身不得再写入 EventRecorder，防止递归**
12. 应用优雅停机时必须先刷完队列
14. `detail` **仅允许白名单字段**；不存异常堆栈，只存 error_type 与简短原因（完整堆栈留在 stdout，靠 trace_id 关联）
16. stdout 的 JSON 日志始终保留，作为数据库不可用时的兜底

## 3.2 保留期

event_log 独立清理开关默认关闭；保留期可配置（默认 30 天），开启后定时分批删除，单批大小可配置。

## 3.3 audit_log 表

字段：id、event、operator、source_ip、target_user_id（完整用户标识）、outcome、detail（jsonb，允许完整业务数据，不含凭证）、created_at。
audit_log 独立清理开关默认关闭；保留期单独配置（默认 180 天）。

必须写入审计的操作：`internal.push.invoked`（谁、推给谁、成功与否）、`user.data.deleted`。
审计写入失败不得影响主流程，但要产生 `persist.failed`。

## 3.4 指标（Micrometer）

本阶段暴露：Webhook 请求数、签名失败数、去重命中数、Reply/Push 失败数、线程池队列长度与拒绝数、落库失败数、`log.dropped`。
AI 相关指标（模型耗时、token、兜底使用数）由后续阶段补充。
若启用 Actuator，仅暴露 health、info 与指标端点，且不得对公网开放，请在计划中说明暴露方式。
