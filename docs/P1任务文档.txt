# 任务

实现智能对话机器人 P1：收到一对一私聊文本消息后，带人设与最近 N 轮上下文调用大模型，并用 Reply 回复。
本阶段**不做**：群聊 AI、消息聚合、拆气泡、打字延迟、引用回复、长期记忆。这些是后续阶段。

## 已确认的取舍与待确认项

1. P1 只为一对一私聊接入 AI；群聊、多人聊天室、缺少 userId 的来源保持现有非 AI 行为，不读取私聊历史。standby 仍仅记录入站、不调用模型、不回复。
2. 保留 Redis 热缓存、串行协调和限流方案；PostgreSQL 为持久化数据源。Redis 环境与连接配置在实施计划中列明，凭证仅从环境变量或外部配置读取。
3. 延续 P0 的尽力异步持久化：数据库写入失败不阻止 Reply；接受故障时部分短期上下文缺失，不承诺不丢记录或完整恢复。可靠持久化队列不在本阶段范围内。
4. 正常 AI 回复、兜底、忙碌及限流提示均记录；默认仅正常 AI 对话参与后续模型上下文。
5. 已确认：P1 采用单实例部署，同一 Channel 同时仅运行一份活动 Java 服务进程，可并发处理不同用户，继续使用 PostgreSQL 与 Redis。
6. 多实例支持不在本阶段范围内。后续升级为多个活动服务副本前，必须补齐共享事件去重、跨实例会话调度和删除协调；仅引入 Redis 锁不能宣称已支持多实例。
7. 模型名称、成本与响应时间目标待项目负责人确定；不得擅自选择模型并把猜测写成已确认默认值。人设文件仍待提供。

1. 先查阅 OpenAI 官方文档，确认当前可用的官方 Java SDK（或官方推荐的调用方式）及最新用法，**不要凭记忆写旧 API**
2. 先输出实现计划（不超过 25 行），包括：新增/修改文件、具体依赖及理由、部署方式、统一超时预算、串行与故障处理、数据迁移方案。补齐限流阈值、队列容量等具体配置建议，不能保留“每分钟 N 条”之类占位默认值。**等我确认后再写代码**
3. 完成后 `mvn clean test` 必须通过
4. 开始实现前核对 P0 的 EventRecorder、审计与指标已实现并验收；不得仅因事件常量存在就认定对应能力可用。缺失时列为前置依赖，不在 P1 中重复实现 P0。

# 一、必须复用 P0 已有能力（不得重复造轮子）

| 需求 | 使用 P0 的能力 |
|---|---|
| 用户历史消息 | 复用 `ChatHistoryService`，现有 findRecent 的 limit 是条数，不是轮数；按需扩展有界查询 |
| 入站/出站消息落库 | 扩展 `ChatMessageService`，写入 model_name、input_tokens、output_tokens、latency_ms 与回复类别、关联标识 |
| 行为事件记录 | `EventRecorder` + `LogEvents` 中已登记的 `ai.*`、`memory.*`、`lock.*`、`user.rate_limited` 常量 |
| 完整业务数据记录 | 使用完整 user_id 与业务原文，不实现 UserRefHasher，不进行 HMAC 或其他脱敏；凭证仍禁记 |
| trace_id 传递 | 既有 MDC 与 TaskDecorator，所有异步路径保持传递 |
| 删除用户数据 | 实现 `UserDataPurger`，使 Redis 上下文也能被 `deleteAll` 清除 |

# 二、包结构

依赖方向扩展为 `webhook → ai → chat/user/messaging`，保留 `messaging → client`；common 不得依赖业务包，不得反向或循环。实现时同步补充 AGENTS.md 中的依赖说明。

新建 `com.example.line.ai`：

```
ai/
├── generation/  ChatModelClient 接口、OpenAI 实现、请求/响应对象、人设加载
├── memory/      ConversationMemory 接口、Redis 实现（短期热缓存）
├── coordination/  会话串行调度、限流与删除协调
└── AiChatService  编排：取上下文 → 调模型 → 校验 → Reply → 确认发送后更新上下文与记录
```

# 三、具体要求

## 3.1 ChatModelClient 接口

1. 业务代码只依赖接口，OpenAI 的类型**不得泄漏**到接口之外
2. 方法：`ChatResult generate(ChatRequest request)`
3. ChatRequest 含：systemPrompt、历史消息列表（role + content）、本次用户消息、当前消息 ID、关联标识、事件时间及剩余调用预算；不包含 replyToken 或 API Key
4. ChatResult 含：回复文本、model_name、input_tokens、output_tokens、耗时
5. 模型名、temperature、超时、最大输入/输出 token、推理强度全部走 `@ConfigurationProperties`。仅发送所选模型支持且已配置的参数；不支持 temperature 时省略，不得无条件指定通用“最低推理档位”
6. OpenAI 原始请求/响应对象只留在适配实现内部，内部角色与用量字段不直接暴露 SDK 类型

## 3.2 OpenAI 实现

1. API Key 仅从环境变量读取（如 `OPENAI_API_KEY`），缺失时启动快速失败；禁止写入日志
2. 从本服务接收 Webhook 开始，以单调时钟计算统一截止时间。排队、同批前置事件、等待串行、Redis/数据库读取、模型调用与重试、LINE 发送均消耗同一预算；预留 Reply 发送时间，进入各步骤前检查剩余预算
3. 原“8 秒”仅作为模型调用预算候选值，不是 LINE 平台有效期。整体截止时间、单次调用、退避、等待锁和发送预留需在模型确定后于计划中给出具体值，并统一现有排队年龄保护；不能给各阶段分别重置完整预算
4. 设置连接、读取及总调用超时，关闭 SDK 自动重试，由应用统一控制：4xx（含 429）不重试；5xx、网络错误、超时最多重试 1 次。退避与再次调用必须有剩余预算，否则立即进入兜底；超过整体截止时间后不再发起新调用
5. 超时后取消可取消的调用并忽略迟到结果，迟到结果不得发送或写回对话上下文。本地取消不证明上游未执行或未计费，不承诺模型调用恰好一次
6. 本阶段只需要纯文本回复。空白、非文本、未完成响应及超长文本必须分类处理；生成结果经过 LINE 文本长度校验再发送，不能用输出 token 上限替代最终校验
7. 超长或无有效文本时，在预算内发送配置兜底；不拆气泡，不静默截断原始模型输出。完整允许业务内容保留在生成事件中，未发送结果不得当作成功出站记录

## 3.3 人设加载

1. 从 classpath 资源 `persona/default.md` 加载 system prompt，支持占位符 `{{current_time}}`、`{{last_chat_gap}}`
2. 当前时间使用 **Asia/Taipei** 时区，格式如"2026年10月14日 星期三 晚上 9:30"
3. `last_chat_gap` 如"距离上次聊天约 3 小时"。以上一条已知私聊用户消息时间与本次消息时间计算，明确排除当前消息及后续消息；不使用本次异步插入结果当作“上次聊天”。无历史时为"这是第一次聊天"，历史读取故障时为"上次聊天时间暂不可用"，不得将故障伪装成首次对话
4. 历史时间可来自已确认的会话快照或数据库；Redis 未命中时通过 ChatHistoryService 查询。时间乱序时差值不为负，时钟可注入，便于确定性测试
5. 文件缺失或为空时启动失败；本阶段不要生成或修改人设内容，由项目负责人提供

## 3.4 短期记忆（Redis 热缓存 + 数据库回源）

1. key 包含应用/Channel 命名空间及 userId，P1 仅存私聊上下文。默认最近 10 轮、写入后 TTL 7 天，均可配置；缓存 TTL 只淘汰缓存，不触发 PostgreSQL 数据删除
2. 一轮定义为一条私聊文本入站及与其关联、已获 LINE 成功响应的正常 AI 文本回复。使用关联标识配对，不能用数据库相邻两条记录猜测。失败、未回复、非文本、原有 echo、兜底、忙碌及限流提示保留原始记录，但默认不作为正常历史轮次；本次用户输入单独加入一次
3. 同时限制轮数和模型输入预算。构造模型请求时优先删除最旧完整轮次，保留人设与当前输入；人设加当前输入本身超限时发送配置提示。不修改数据库或日志原始内容，不生成摘要冒充原文
4. 先读 Redis，未命中则通过 ChatHistoryService 有界查询、筛选并回填，记录 `memory.cache_miss`（DEBUG）。查询需支持排除当前消息和会话快照边界，不直接把 N 作为 findRecent 条数；查询上限、筛选不足时的行为均需明确
5. 正常路径以内存中的当前串行会话快照连接尚未落库的上一轮，再更新 Redis；按入站消息 ID 去重合并，禁止无界缓存。Redis/进程故障后仅能恢复数据库中已经持久化的历史，不承诺恢复仍在异步队列中的消息
6. Reply 成功后才把该回复加入已发送上下文。生成成功但发送失败/结果未知时，不添加该 assistant 消息；缓存更新失败不得让已成功 Reply 的事件重新执行
7. Redis 故障时暂停 AI 调用，在剩余预算内尝试配置的服务暂不可用提示，保留原有异步落库和失败记录。缓存未命中但数据库查询失败时也采用此策略，不无约束调用无历史模型。故障恢复后允许数据库回源
8. Redis 数据视为可丢弃，不作为唯一持久化来源。实现 UserDataPurger，并按 3.10 节与在途请求协调；所有新增用户缓存和协调状态均需说明清理方式
9. 通过允许字段完整记录实际发送给模型的业务上下文与生成结果，不直接打印 SDK 对象或带鉴权的请求信封；字段白名单与事件必须先登记

## 3.5 接入 webhook

1. `MessageEventHandler` 中仅 active 的一对一私聊文本交给 AiChatService；其他来源及类型保持现有行为。私聊历史查询必须能排除原有群聊记录；若旧表无法可靠区分来源，旧数据不纳入 AI 历史，仍完整保留
2. 回复使用 replyToken，**一次性使用，不得存储**
3. 复用现有异步执行设施并增加有界会话调度，不得阻塞 Webhook 的 200 响应。当前事件凭证只用于当前短时处理，不写入数据库、Redis、日志、重试作业或供以后恢复的任务
4. 保留入站异步落库。Reply 获得成功响应后异步记录出站消息；这表示 LINE 接受请求，不承诺终端用户已经阅读或收到
5. 模型失败、超时、无有效输出时，在剩余发送预算内尝试配置兜底，记录 ai.generate.failed 与 ai.fallback.used。忙碌、限流、依赖故障分别分类；未调用模型的拒绝不能计为模型生成失败
6. 所有提示话术从配置读取并校验非空及发送长度。发送失败、Token 失效、队列拒绝必须可观测；不承诺每条请求必达，不改变现有 HTTP 确认策略。Reply 已发起而结果未知时，不再用同一 Token 补发兜底，也不自动改用 Push
7. 扩展 recordOutbound 接口，保存 model_name、input_tokens、output_tokens、latency_ms、reply_kind、关联入站消息 ID 和会话来源。正常 AI 使用真实生成用量，提示类 model_name 和用量为空；生成失败或生成成功但发送失败的用量保留在事件记录中
8. reply_kind 至少区分 AI、FALLBACK、BUSY、RATE_LIMITED、SERVICE_UNAVAILABLE、INPUT_TOO_LONG、LEGACY。表变更使用新增 Flyway 迁移；旧记录标记为 LEGACY/未知来源，不伪造关联或来源。具体字段名与索引在计划中列明

## 3.6 同一用户串行处理

1. 单实例方案按本服务接收顺序为同一用户串行处理；同批按事件顺序进入调度。使用有界用户队列/调度器，不以抢锁顺序冒充消息顺序；不保证重投递或网络乱序后的原始发送顺序
2. 等待中的同用户任务不得占满所有 Webhook 工作线程；限制每用户与全局排队容量，全部任务沿用入口截止时间，过期任务不再调用模型
3. 使用 Redis 锁时设置 TTL、唯一持有者和原子校验释放；锁的有效期覆盖剩余处理与提交预算。持有权丢失后禁止继续发送或写回，验证与更新须防止检查后竞争；无法彻底避免的远端在途副作用需如实说明
4. 等待串行/锁超限或队列满时，在发送预算内尝试配置忙碌提示并记录原因；锁等待超时记录 lock.timeout。提示不进入正常历史轮次，不能继续调用模型绕过并发限制
5. 多实例方案须另行确认：共享 webhookEventId 去重、跨实例有界排序、锁续期/过期与删除协调。单实例上线时明确禁止多个活动副本，包括滚动发布时短暂重叠；切换多实例前先完成这些能力

## 3.7 频率限制

1. 单用户频率限制使用 Redis 原子计数与 TTL；阈值、窗口、提示话术均可配置，具体初始值在实施计划中列出。P1 不做消息聚合，连续短消息各算一条；已去重事件不重复计数
2. 超限时回复一句自然的提示话术（话术走配置），记录 `user.rate_limited`
3. 限流计数丢失（Redis 重启）可接受，请在文档说明
4. 限流在模型调用前执行，计数更新与首次设置过期需原子完成；Redis 故障按 3.4 节暂停 AI 并提示，不默认无限放行

## 3.8 安全

1. 用户消息只放在 user 角色，**禁止拼接进 system prompt**
2. 日志、event_log、audit_log、业务表保留完整 user_id、用户原文、AI 回复和允许的业务元数据，不截断、不脱敏。API Key、各类凭证 Token、签名及数据库/Redis 密码禁止记录
3. 记录事件时使用 user_id，detail 只放已登记白名单字段；允许字段覆盖完整业务上下文与结果。禁止把 Authorization、请求头或带凭证的完整请求体混入日志，SDK/HTTP 调试日志也需验证
4. input_tokens/output_tokens 是模型用量，不是凭证 Token；按独立数值字段记录，不因凭证过滤而误删。实际模型调用使用的历史保留原有角色，不把历史用户文本提升为 system 指令

## 3.9 事件与指标（使用 P0 已登记的事件常量）

- `ai.generate.success`：duration_ms、model、input_tokens、output_tokens
- `ai.generate.failed`：error_type（超时/4xx/5xx/限流等）、duration_ms
- `ai.fallback.used`
- `lock.timeout`、`user.rate_limited`、`memory.cache_miss`
- 新增指标：模型调用耗时分布、失败数、token 用量、兜底使用数、锁超时数
- 模型生成、LINE 接受发送、异步持久化分别记录结果；提示尝试与发送成功分开计数。重试按 attempt 统计，并提供逻辑请求总耗时，未知用量不伪造为零
- 指标标签不得使用 userId、trace_id、消息原文等高基数字段；这些完整数据保存在业务日志/事件字段中
- 原事件无法表达的生成请求、缓存故障、排队拒绝、删除协调事件，先在日志规范登记再增加常量，不动态拼接事件名

## 3.10 数据删除与保留

1. 取消关注只更新状态，重新关注恢复状态；所有业务数据清理开关沿用 P0，默认关闭。Redis 缓存 TTL 不改变这些规则
2. 显式 deleteAll 前建立用户处理屏障：阻止该用户新的 AI 工作进入、取消/排空待处理任务，等待正在执行的发送和异步持久化任务在限定时间内结束，再调用全部 Purger。无法安全完成时明确失败，不假报删除成功
3. 删除过程避免在数据库事务内长时间等待；PostgreSQL 本地事务不能回滚 Redis，外部清理必须幂等、可重试，失败写审计和明确结果。不得直接删除另一个在途持有者的锁
4. 删除完成后，旧任务不得回填缓存或数据库；屏障解除后收到的新消息可开始新的历史。多实例时屏障和在途协调也必须共享，不能只使用本地标记

# 四、测试要求

- 单元测试 mock `ChatModelClient`，**不得调用真实 OpenAI 接口**
- 必须覆盖：
  - 正常回复并正确落库（入站 + 出站，出站含 model/token/latency）
  - 模型超时走兜底、兜底出站消息的记录方式
  - 4xx 不重试、5xx 重试一次且不超时间预算
  - 上下文裁剪到 N 轮；Redis 未命中从数据库回源并回填
  - 条数与轮数区别、关联配对、非文本与提示过滤、输入预算、原始内容不被裁剪
  - 当前消息只发送一次、上一轮尚未落库、回源排除当前与未来消息、首次与读取失败区分
  - 群聊/多人聊天室不读取私聊历史、旧来源未知记录不进入 AI 上下文、standby 不调用模型
  - 生成成功但 Reply 失败/结果未知不写成功出站、不污染历史；Reply 成功后缓存失败不重复发送
  - 排队、锁等待、依赖调用、模型重试与 Reply 共享截止时间；关闭 SDK 隐式重试；迟到结果无副作用
  - 空白/非文本/未完成/超长结果、配置话术校验、剩余预算不足及发送失败可观测
  - 同一用户串行、锁 TTL、拿不到锁的行为
  - 接收顺序与抢锁顺序不同、多用户不互相占满等待线程、队列上限、锁失效后旧持有者不能提交
  - Redis/数据库故障提示、缓存重建、已确认持久化限制下的历史缺失
  - 频率限制与超限话术
  - 人设占位符替换（Asia/Taipei 时间、首次对话、间隔文字）
  - `purge(userId)` 清除 Redis 上下文，并被 `UserDataDeletionService.deleteAll` 调用
  - 删除与在途生成/发送/持久化竞争，清理失败可重试，删除完成后旧任务不能重新写入
- **日志泄露测试**扩展：使用虚构数据覆盖完整 AI 流程，验证日志与 event_log 完整保留 user_id、消息、上下文、回复等允许业务字段；对假 API Key、replyToken、quoteToken、签名、密码等凭证断言不泄露。原有凭证断言不得弱化
- DocumentedFlowIntegrationTest 保持有效并补充 AI 回复流程
- 所有 Redis、PostgreSQL 相关测试使用 Testcontainers
- SDK 适配层使用本地模拟 HTTP 服务验证请求参数、错误分类、重试次数和超时；不调用真实模型。并发/截止时间优先使用可控时钟与同步工具，不依赖长时间 sleep
