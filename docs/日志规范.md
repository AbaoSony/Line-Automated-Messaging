P2 第三阶段新增已触发事件：`ai.turn.admitted`（逐成员准入）、`ai.turn.decided`（规则建议与应用结果）、`ai.turn.completed`（每个成员共享的明确轮次终态）。新业务细节白名单：`turn_id`、`member_count`、`input_version`、`generation_version`。生成请求的 `content.current_messages` 保存各成员完整原文及原始业务标识，发送凭证不进入任何业务快照。以上事件与既有事件相同，经有界异步队列写入 event_log；每个成员终态日志恢复该成员自己的 trace。

## 凭证边界

禁止记录或存储 Channel Secret、Access Token、内部接口 token、API Key、数据库密码、
replyToken、quoteToken、markAsReadToken、完整签名或包含它们的原始请求头/完整 Webhook 请求体。
可以记录完整 `user_id`、消息原文、回复和非文本业务元数据。按字段选择内容，禁止直接打印 SDK 事件对象。
JDBC/SDK 异常可能携带凭证，业务失败只输出异常类型、cause/suppressed 调用帧，不输出原始异常消息或绑定参数。
凭证过滤按字段进行，用户文本和回复不进行关键词替换或脱敏。框架日志不输出原始摘要和异常消息，
只保留组件、级别、链路与安全调用帧；配置失败额外列出已知配置名称，保证启动报错可以定位缺失项。

## 字段

| 字段 | 含义与状态 |
| --- | --- |
| event | 使用 LogEvents 已登记常量 |
| trace_id | 服务端请求 UUID；同一请求的多事件共享；异步后台任务无请求时生成独立 UUID，框架/启动日志使用进程级背景 UUID |
| user_id | 原始完整用户标识，无用户上下文时可为空 |
| operation | 持久化业务事件名，或 event_log / audit_log 及其清理操作标识 |
| error_type | 异常类名，不包含凭证 |
| delivery_outcome | 第四阶段已触发，失败/重试 detail 字段：NOT_SENT / REJECTED / UNKNOWN；不改变顶层 outcome 枚举 |
| ts、level、service、env、version、instance | 每条固定包含；ts 为 UTC ISO-8601；其余配置来源与默认值统一见接口文档第 2 节 |
| webhook_event_id、outcome、duration_ms、http_status、message_type、message_id、text_length | 按事件记录；outcome 使用 SUCCESS / FAILED / SKIPPED；时长单位毫秒 |
| model、input_tokens、output_tokens | P1 已实现；生成事件记录实际模型与已知用量，未知为空；提示不伪造模型统计 |
| content、messages | 完整业务数据或待发消息，递归排除凭证字段；不存二进制，不保存原始报文 |
| logger、thread、stack_trace | 组件、线程与安全调用帧；框架日志使用 app.lifecycle |
| configuration_fields | 启动配置错误中的已知配置名称列表，不包含配置值 |
| operator、source_ip、target_user_id | 敏感操作的稳定操作者标识、直接连接地址与完整目标用户；共用内部 token 的操作者名为 internal-token，手动 Java 删除为 manual |
| record_id、persistence_fallback | 数据库批写最终失败时的 UUID 与 stdout 兜底标志，仅兜底记录出现 |

## 保留与排查

聊天、事件日志、审计日志分别配置独立清理开关，默认关闭；启用时默认保留 90/30/180 天。
三个独立清理任务均已实现；每次只清理一批，具体配置与间隔统一见接口文档第 2 节。
按 HTTP 响应的 X-Trace-Id 检索 stdout，可以关联 user.message.received、line.reply.requested、line.reply.sent、persist.failed 等记录。
一次响应 200 不能证明数据库写入成功，需结合 persist.failed 排查。记录样例见 [虚构日志与响应](examples/webhook/README.md)。
stdout 事件不代表已经落库；日志队列满、数据库失败、进程崩溃可能导致仅有 stdout 记录。

EventRecorder 只接收应用中显式带 LogEvents 的结构化日志；框架消息和未登记日志不进入事件队列。
`persist.failed` 永不入队，防止日志存储自身故障递归；已有 stdout JSON 始终保留。
队列中只放已复制、已排除凭证的 JSON 字段，不放原始 Webhook、SDK 事件或 Throwable。
同一队列服务 event_log 与 audit_log，后台批写由固定 UUID 保证重试幂等；只重试一次，失败后 stdout 兜底。
队列拒绝累加 log.dropped；审计拒绝（含删除屏障或工作容量拒绝）额外记录 persist.failed。已接收的队列在优雅停机时刷完后才关闭日志池。

event_log.detail 与 audit_log.detail 使用同一白名单：
`operation`、`attempt`、`retry`、`active`、`queued`、`shutdown`、`message_id`、`text_length`、
`content`、`messages`、`is_redelivery`、`reason`、`correlation_id`、`reply_kind`、`stage`。
content/messages 的完整文本和业务元数据递归排除凭证字段；reason 由代码提供固定短原因，不传异常原文。
error_type 使用独立列或 stdout 字段；stack_trace 不进入数据库。事件固定字段作为列保存，审计通过 trace_id 列关联 stdout。
内部推送仅在通过鉴权并调用发送服务后记录操作审计；手动删除提交/回滚之后记录真实 SUCCESS/FAILED。
历史日志通过 UserDataPurger 随显式删除清理，本次删除操作的事件和审计作为新操作记录继续保留。

排查 SQL（trace_id 全部为虚构占位，运行时替换为响应中的值）：

```sql
SELECT ts, event, user_id, outcome, error_type, detail
FROM event_log
WHERE trace_id = '11111111-1111-4111-8111-111111111111'
ORDER BY ts, id;

SELECT created_at, event, operator, source_ip, target_user_id, outcome, detail
FROM audit_log
WHERE trace_id = '33333333-3333-4333-8333-333333333333'
ORDER BY created_at, id;
```

同 trace 的 persist.failed 只在 stdout；数据库中查不到对应记录时，结合 log.dropped、persist.failed 与兜底标志排查。
完整虚构表行见 [event_log](examples/webhook/event-log.json) 与 [audit_log](examples/push/audit-log.json)。

local profile 默认追加写入 logs/application-readable.log，stdout 仍为 JSON。
易读文件带时间、级别、trace_id、event 前缀和同一份详细字段，使用 UTF-8；换行转义为单条记录。
未启用 local profile 时不创建该文件；本地文件不自动删除或轮转，用户手动处理，目录已被 Git 忽略。

格式器使用 [Spring Boot 3.5 内置结构化日志扩展接口](https://docs.spring.io/spring-boot/3.5/reference/features/logging.html#features.logging.structured)，未新增日志依赖。

## P1 业务数据与指标

`ai.generate.requested.content` 保存完整 system_prompt（负责人原人设替换时间占位符）、角色 history 与 user_message；历史裁剪只影响这次实际模型请求，入站原文独立保留。`ai.generate.success/failed.content` 保存完整实际生成 text、status、incomplete_reason、reasoning_tokens，包括未完成、空白或超长结果，不静默截断。模型 SDK 的请求/响应对象及 HTTP 信封不能直接输出。

`ai.generate.retry` 记录每次失败尝试的 attempt/retry/http_status/error_type/duration_ms；SDK 自动重试关闭。`ai.generate.failed` 表示实际生成失败，忙碌、限流、依赖故障分别使用对应事件。`ai.fallback.used` 表示预算内尝试兜底，不等同送达；`line.reply.sent` 才表示 LINE 已接受。Reply 结果未知不补发。已发送后缓存故障只记 `ai.dependency.failed`，不重新生成或发送。

用量以模型实际响应为准，可能包含推理输出计费；未知用量不记成零。指标区分单次尝试、逻辑耗时、生成失败、提示尝试与接受，具体名称与默认资源边界统一见接口文档 2.5。生产 INFO 不输出 DEBUG cache_miss；排查可临时调整该应用日志器，禁止启用 SDK HTTP 或 Redis/JDBC 凭证调试日志。

删除屏障中的旧用户事件仍可在 stdout 观察，但不再写回数据库；本次 user.data.deleted 事件与审计作为新的操作证据保留。完整数据默认保留，清理开关仍相互独立且默认关闭。

生成未完成原因只记录供应商固定枚举 max_output_tokens/max_messages/content_filter/steered；其他值归为 unknown，缺失为空，不输出供应商未知字符串或完整 SDK 响应。推理用量来自响应 usage.output_tokens_details.reasoning_tokens，缺失保持 null；它已包含在 output_tokens 中，不重复累加。输出额度耗尽仍走配置兜底，真实生成用量保留，既不重试未完成响应，也不把无正文的 assistant 放入上下文。

`ai.queue.rejected` / BUSY 是同用户等待超时或队列容量拒绝，尚未调用模型；默认只记录 BUSY 而不发送提示，稍后原任务仍可发送自身的正常回复；显式开启技术提示时才可能先发送 BUSY。`ai.generate.failed` / FALLBACK 则是生成失败或无可发送正文。虚构结果字段见 [ai-generation-incomplete.json](examples/webhook/ai-generation-incomplete.json)。

## 技术提示静默（已实现）

`AI_TECHNICAL_REPLIES_ENABLED=false` 为新默认：FALLBACK、BUSY、RATE_LIMITED、SERVICE_UNAVAILABLE、INPUT_TOO_LONG 不调用 LINE，不写成功出站，不加入正常上下文。复用 `ai.reply.skipped` 登记固定 reason=technical_replies_disabled，reply_kind 保存原分类，outcome=SKIPPED。原始入站、生成结果、ai.generate.failed、ai.queue.rejected、lock.timeout、user.rate_limited、ai.dependency.failed 与相关失败指标继续记录。

静默不计 ai.fallback.attempted/accepted，不输出表示兜底尝试的 ai.fallback.used 或 line.reply.requested/sent，不伪造成功发送。只有显式恢复开关后才按原有预算尝试技术提示；正常 AI Reply 不受该开关影响。

P2 第四阶段提示冷却满时使用已登记 ai.reply.skipped，reason=technical_reply_capacity，仍无提示出站或自动补发。中断后的 owner 释放失败仍沿用 ai.dependency.failed，不输出 Redis 原始错误信息。

第七阶段还复现并修复连续删除审计竞态：本次删除事件/审计允许越过自己的屏障入队，但持有独立工作租约至实际写入退出；下一次删除必须等待前一轮记录后再清理历史。RecordQueueTest 先复现旧实现漏等，再验证修复；不阻塞业务线程写日志，不改变审计失败隔离或默认数据保留。
