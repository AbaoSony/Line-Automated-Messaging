# 任务

实现 P2：对一对一私聊文本消息增加"聚合窗口"。首次生成前收到的连发文本组成一次逻辑生成、最多一次 Reply 尝试；模型重试和有界重生成可能产生多次模型请求。窗口时长按内容动态调整，并始终受 P1 统一截止时间约束。

本阶段**不做**：拆气泡、打字延迟、Loading Animation、引用回复、由模型判断回复策略、Push 补发、长期记忆、群聊聚合、多实例支持。这些是后续阶段。

后续产品方向已明确：让模型结合上下文参与判断回复时机，目标是自然、有分寸的对话节奏。P2 只提供可替换的规则策略与可靠执行机制，扩展边界见第八节，不提前接入额外策略模型。

## 已确认的取舍与待确认项

1. **聚合缓冲放在进程内存，不放 Redis**（调整原路线图中的"Redis 缓冲"）。原因：当前即时处理持有 replyToken，凭证禁止持久化；P1 已确认单实例，本阶段不提供重启恢复。进程重启会丢失本地令牌引用，不代表 LINE 自动使令牌失效。Redis 仍只用于 P1 已有的上下文缓存、限流与协调，**本阶段不新增 Redis 用途**（AGENTS.md 第 13.5 条）。
2. **一个聚合批次只使用本批次内最新、通过准入且具备可用 replyToken 的事件令牌**。较早令牌被替换后释放且不使用。允许在当前即时回复流程中有界、短暂持有，覆盖聚合、排队、生成和发送，禁止持久化；实施前按 3.4 节同步修订 AGENTS.md 第 5.2 条，不能只写“窗口内持有”。
3. **仅使用 Reply，不引入 Push。** 预算不足时提前结束窗口；仍不足以调用模型时按 P1 规则尝试配置兜底，再不足则放弃并记录，不补发 Push。Reply/Push 取舍留给后续阶段。
4. **窗口规则为确定性的规则引擎，不调用大模型**，参数全部可配置。由模型判断回复策略属于后续阶段。
5. **生成中收到新消息时可撤销重生成；Reply 发起后不可撤销。** 初始最大重生成次数为 1，配置为 0 可关闭；次数、首条接收时刻和批次硬截止时间不因回到收集状态而重置。
6. **非文本消息保持 P1 现有行为**，不加入批次、不重置窗口。这是已知的体验限制，需在文档中说明。
7. 一个批次对应多条入站消息，**"一轮"的定义与关联字段需要调整**（见 3.5），需要新增 Flyway 迁移。
8. 采用 1.5 / 2.5 / 3.5 秒窗口、首条起最多收集 6 秒、最多重生成 1 次、提示共用 10 秒冷却作为初始调参基线。批次容量、全局容量、总存活时间在实施计划中给出具体值；模型与整体响应目标以 P1 最终验收配置为准，未确定时不得猜测。
9. 多实例仍不在范围内，沿用 P1 的单实例约束与前置条件。

# 三、具体要求

## 3.1 批次与状态机

1. 每个私聊用户在进程内存中最多一个会话，由单一协调器拥有。至多一个活动批次与一个有界待处理批次；两者的消息、令牌、计时和容量独立。活动状态至少包含 IDLE、COLLECTING、GENERATING、SENDING。待处理批次也从自身首条接收时刻计时，不能等转为活动批次后才开始计算预算。
2. 接收流程：原始字节验签 → 分配接收序号并有序发布到有界内存接收队列 → 快速返回 200。接收线程不等待 Redis、数据库、模型或 LINE。异步按接收顺序解析、去重、记录入站、限流，再准入聚合批次；“接收队列”与“已获准批次”必须区分。序号分配和发布需协调，不能只用原子计数后任由线程乱序入队；同请求内按 events 顺序处理。记录并计量准入拒绝，不声称过载时可靠投递。
3. `COLLECTING` 中每来一条新消息，重新计算窗口截止时间，受 3.2、3.3 约束。
4. GENERATING 中收到新文本：只有仍未到最长收集时间、容量允许、剩余预算足够且未达重生成上限时，才使当前生成版本失效、尝试取消调用、并入消息并回到 COLLECTING。否则新消息进入待处理批次。每次生成带 generation_version；过期版本的结果不得发送、写回上下文或记为成功出站。检查版本和进入 SENDING 必须原子完成，避免取消与发送竞争。
5. 取消本地调用不保证上游停止或不计费；已取消但尚未结束的本地请求仍计入在途资源上限，不通过取消绕过并发限制。已知用量记事件，未知不伪造为零；重生成计数与每次调用的重试计数分别记录，整体物理请求次数与时间均需有限。
6. `SENDING` 中收到的新文本一律进入下一个批次，不得与已发起的 Reply 竞争。
7. 单批次消息条数与字符数在加入前校验：达到上限立即结束窗口，下一条会超限时转入待处理批次；单条自身超限按 P1 输入过长规则处理，不截断原文。接收队列、每用户待处理量、活跃会话总数、总字符数和在途请求均有上限，满载按 P1 忙碌规则处理。实际容量与字符计量单位在计划中列出。
8. 已被去重的事件不得重复加入批次或重复计数；首次见到 isRedelivery=true 的事件仍按正常资格检查，不能仅凭重投递标记丢弃。入队成功只代表受理，批次结束另记结果；被撤销的生成不能释放其成员事件去重记录，导致重复准入。停机后内存去重丢失的限制须说明，不承诺跨重启恰好一次。
9. 等待窗口不得占用工作线程：使用有界定时调度，到期只向协调器发布事件，再提交生成。取消定时任务要移除队列引用，迟到的到期回调按批次/版本丢弃，不能重复触发。禁止每用户一个线程或长时间 sleep；任务提交被拒绝也须终结或降级并释放资源。

## 3.2 动态窗口规则

1. 以纯函数实现 `窗口时长 = f(最后一条消息内容, 与上一条的间隔, 批次内条数)`，时钟可注入，便于确定性测试；不调用模型。

2. 至少区分：

   - 看起来已说完（以句末标点结尾、疑问语气词结尾等）→ 较短窗口
   - 看起来没说完（以逗号、顿号、省略号或连接词结尾，或极短且无标点）→ 较长窗口
   - 其余 → 默认窗口
   - 连发节奏很快（与上一条间隔低于阈值）→ 在上限内适度延长

3. 标点集合、连接词与语气词清单、各档时长、节奏阈值全部来自配置，不硬编码。默认词表以**台湾繁体中文口语**为目标；其他语言走默认窗口，不得因此报错。

4. 区分两个上限：最长收集时间从批次首条接收起计，达到后不再合并新消息并开始处理；批次最大存活时间覆盖全部处理，达到后不再发起生成或发送，未发送批次终结。已发起发送按 SENDING 的结果未知规则收尾。新消息和重生成都不得重置这两个起点。

5. 初始调参基线：已说完 1.5 秒、默认 2.5 秒、没说完 3.5 秒、首条起最长收集 6 秒；实际等待取规则值与剩余预算允许值的较小者。规则冲突须确定优先级（如省略号优先于普通句末标点），不把语气词当作真实意图保证。配置可调整，并用虚构/经授权的对话进行校准。

## 3.3 时间预算

1. 每条事件沿用 P1 从接收时刻生成的单调时钟截止时间 D_i，不因准入、开始生成或收到新消息而重置。批次硬截止时间 D = min(全部成员的 D_i, 首条接收时刻 + 最大存活时间)。最新令牌仍受它自身原始截止时间限制；更换令牌不能延后旧成员的处理预算。
2. 窗口结束时间 ≤ min(最后一条接收时刻 + 规则窗口, 首条接收时刻 + 最长收集时间, D − 排队/上下文/协调预留 − 模型调用预算 − 发送预留)。计算结果已到期时立即结束收集；真实排队可能超过预留，因此每阶段仍需检查实际剩余预算。生成与重试共享模型预算，不能各自取得完整预算。
3. 剩余预算不足以调用模型：按 P1 规则尝试配置兜底；不足以发送：放弃该批次并记录原因，**不补发 Push、不存令牌待后用**。
4. 撤销重生成沿用同一批次标识、首条接收时刻、累计重生成次数与硬截止时间，旧调用已消耗时间不可回收。真正的下一批次按其成员原始接收时刻计算预算，等待前批次结束的时间也计入。
5. 计划中必须给出预算分解表和可用窗口上限，统一 P1 排队年龄保护。6 秒仅是收集上限，不是整轮响应时间；若模型需 8 秒，还需另计发送及其他开销。配置不相容时清晰报错或明确说明窗口会被压缩，不能隐藏预算矛盾。

## 3.4 replyToken 处理

1. 仅保留本批次内最新、通过准入且具备可用令牌的事件令牌，较早令牌被替换后释放引用且不使用。重复、超限、无令牌和属于下一批次的事件不得替换当前令牌；无法资格校验的消息按 P1 跳过/提示规则处理并记录。
2. 令牌仅在当前即时处理所需的进程内存中存在，包括有界接收队列、活动/待处理批次及实际发送调用；不得写入数据库、Redis、日志、事件 detail、持久化队列或可恢复任务。替换、完成、放弃、超时后释放业务引用；不得声称清除引用等同于安全擦除 JVM 或 SDK 的全部内存副本。
3. 令牌一次性使用；发送结果未知时不得用同一令牌补发兜底，沿用 P1 规则。
4. 本文给出规则修订要求，当前文档编辑不代表根规则已修改。P2 编码前将 AGENTS.md 第 5.2 条同步修订为：

   > replyToken 一次性使用、有效期很短。仅允许在当前即时回复流程的进程内存中有界、短暂持有，覆盖聚合、排队、生成和发送阶段，并受统一截止时间约束；禁止写入数据库、Redis、日志、持久化队列或可恢复任务。替换、完成、放弃或超时后释放业务引用，发送结果未知时不得重复使用。

5. 同步澄清 P1 中“不得存储”的含义为禁止持久化和跨流程延迟复用，保留 P1 当时的一对一轮次定义，并注明 P2 的后续扩展，避免历史阶段文档相互矛盾。

## 3.5 "一轮"定义、数据模型与上下文

1. 一轮 = 一个已获 LINE 成功响应的正常 AI 回复 + 对应的一条或多条同批次入站文本。采用批次标识、成员关联表及出站关联表达，成员保存消息 ID 与批次内顺序；约束同一会话内不重复归属正常已发送轮次。具体表名、唯一约束、查询与清理索引在计划中列出，不用相邻记录猜测。新增 Flyway 迁移，不改已经应用的脚本。
2. P1 有明确有效关联的“单条入站 ↔ 回复”迁为单成员批次；关联不完整时保留原始记录并排除默认历史，不伪造配对，LEGACY 语义保持。迁移前核对 P1 实际字段与数据，不仅依据任务文档推断。
3. 成功出站记录及其成员关联作为同一异步业务事务写入，使用稳定标识保证可重试/幂等。明确入站尚未落库时的关联处理，不能因外键竞争阻塞 Reply 或只留下半套成功关联；历史查询仅使用完整已配对轮次。失败沿用 P0 尽力记录限制并记日志/指标。
4. 批次中的原始入站消息**逐条保存、保持原文与顺序**，不合并改写。构造模型请求时保留消息边界与先后顺序，不生成摘要冒充原文；`ChatRequest` 由单条当前消息扩展为当前批次的消息列表（含消息 ID、事件时间），仍不包含 replyToken 与 API Key。
5. 出站回复记录关联该批次全部入站消息 ID；`reply_kind` 规则沿用 P1。失败、兜底、忙碌、限流、被撤销的生成不进入默认历史轮次，原始记录完整保留。
6. `last_chat_gap` 以**批次首条消息之前**最近一条已知私聊用户消息的时间计算，排除当前批次全部消息；历史读取故障时的表述沿用 P1。
7. 内存会话快照用于连接尚未落库的上一轮；按入站消息 ID 去重合并，保持有界；Reply 成功后才把该回复及其批次加入已发送上下文（沿用 P1 3.4）。缓存更新失败不得让已成功 Reply 的批次重新执行。
8. Redis 历史结构升级须带格式版本或使用新 key 命名空间；遇到旧缓存回源数据库，不把旧单条格式当多条读取。废弃 key 依 TTL 淘汰，显式删除覆盖新旧命名空间；这属于原上下文缓存用途，不新增 Redis 业务用途。
9. 保留与手动删除覆盖新增批次及关联记录；缺失部分成员的批次不作为完整轮次回传。历史裁剪按完整批次和输入预算进行，不截断已存原文；当前批次本身超输入预算按 P1 提示策略处理。

## 3.6 与限流、忙碌、容量的配合

1. 限流沿用 P1：每条有效文本计一次，由异步按序处理器在去重后、准入聚合批次前执行，不在 HTTP 接收线程等待 Redis。超限消息仍逐条提交异步入站记录，但不加入批次；这不改变 P0 在持久化失败/全局入队拒绝时可能丢记录的限制。
2. 限流、忙碌、容量满、服务暂不可用提示共用用户级冷却，初始 10 秒内最多尝试发送一次。原子占用提示机会，以尝试时刻开始固定冷却，不随新消息滚动延长；失败/结果未知也占用机会。提示不进入正常历史轮次。冷却状态仅在有容量和过期清理的本地结构中，容量不足时保守抑制提示并计数，不能无界增长。
3. 提示只使用触发该提示、未准入批次的事件令牌，不占用活动或待处理批次令牌。发送仍通过会话协调器，不能与正常 Reply 并发争抢状态；预算已耗尽时记录未发送。提示抑制不丢弃对应入站记录。
4. Redis 或数据库故障沿用 P1 3.4 的暂停 AI 与提示策略，不无约束地调用无历史模型。

## 3.7 非文本、生命周期与停机

1. 非文本事件保持 P1 现有行为，**不加入批次、不重置或延长窗口、不触发提前结束**；在文档中说明这一体验限制。
2. 群聊、多人聊天室、缺少 userId 的来源、standby 保持 P1 行为，不进入聚合。
3. 经去重和状态新旧判定后有效的取消关注事件，使该用户待处理/收集批次终结并取消生成，禁止新发送；旧重投递不能取消重新关注后的新会话。已进入 SENDING 的请求不可撤回，限定时间内记录成功/失败/结果未知，不假称消息已取消。数据保留仍仅更新关注状态，保留全部原始记录。
4. 优雅停机：先关闭准入，取消待处理/收集批次的定时与生成，记录放弃；对 SENDING 限时等待并记录实际结果，超时为结果未知。停止业务生产者并完成受限持久化等待后，再刷事件/审计队列，最后关闭资源。不恢复批次、不补发 Push；突然崩溃无法保证写出放弃日志，已落库入站可能无回复。单实例更新禁止活动副本短暂重叠。

## 3.8 删除协调

1. 接入 P1 的删除屏障：`deleteAll` 阻止该用户新批次进入，清空缓冲、取消窗口定时与在途生成、释放令牌，等待正在发送和持久化的任务在限定时间内结束，再调用全部 Purger。无法安全完成时明确失败，不假报成功。
2. 删除完成后旧批次与迟到结果不得回填缓存或数据库；屏障解除后的新消息可开始新历史。
3. 聚合缓冲中的用户数据同样须说明清理方式，并纳入 `UserDataPurger` 约定。
4. 删除范围包含活动及待处理批次、定时回调、提示冷却、新旧 Redis 缓存、数据库批次成员关联；失效版本的回调不得在删除后重建状态。沿用 P1 对在途消息、业务持久化及 P0 事件/审计排空的协调，本次删除审计按根规则保留。

## 3.9 事件与指标

1. 新增事件须先在 `docs/日志规范.md` 登记，触发代码交付后才标记已触发；不动态拼接事件名。建议：

   - `ai.turn.flushed`：结束原因（窗口到期 / 最长等待 / 条数或字数上限 / 预算限制）、消息数、聚合等待时长、撤销次数
   - `ai.turn.superseded`：被撤销的生成及其已知用量
   - `ai.turn.abandoned`：原因（取消关注 / 停机 / 删除 / 预算耗尽 / 容量）

2. 沿用 `ai.generate.*`、`ai.fallback.used`、`user.rate_limited`、`lock.timeout`。detail 只使用已登记白名单字段；AGENTS.md 第 9 节允许保留完整业务内容，但令牌、签名、密钥禁记。

3. 指标：批次大小分布、聚合等待时长、结束原因计数、撤销次数、放弃次数、活跃会话数、缓冲消息数。标签不得使用 userId、trace_id、消息内容等高基数字段。

4. 模型生成、LINE 接受发送、异步持久化分别记录结果；提示尝试与发送成功分开计数（沿用 P1）。
5. 增加 batch_id 与 generation_version；保留成员各自的 webhook_event_id、message_id、trace_id、接收顺序，不用最新消息的 MDC 覆盖其他成员的身份。批次操作选择并固定主 trace_id，通过成员关联追溯全部入口；这些标识不作指标标签。

## 3.10 安全

1. 用户消息只放 user 角色，禁止拼接进 system prompt；批次内多条消息同样遵守。
2. 日志、event_log、audit_log 允许完整 user_id 与业务原文；replyToken、quoteToken、markAsReadToken、签名、API Key、数据库/Redis 密码**禁止记录**。批次对象不得被整体打印（避免 toString 泄露令牌）。
3. 业务线程不得等待日志队列，保持 P0 的有界、丢弃并计数规则。

# 八、后续扩展：模型参与回复时机判断（未实现，不计入 P2 验收）

## 8.1 产品目标

1. 追求自然、连贯、有分寸的交流：用户尚未说完时等一等，明确提问或紧迫表达及时回应，简短确认不机械生成长篇回复。不能以“延迟越长越像真人”作为优化目标。
2. 自然感同时依赖对话记忆、人设一致性、表达长度与语气、话题衔接和时机。回复时机策略只负责其中一部分，不假造现实经历、忙碌理由或真人身份来解释等待。
3. 区分“等用户补充再生成”和“内容已生成但稍后发送”；后者属于后续发送时机控制，不能通过反复重生成制造延迟。P2 不实现打字延迟或长期静默。

## 8.2 P2 保留的最小扩展边界

1. 将确定性窗口规则封装为 ReplyTimingPolicy 或等价纯策略入口，返回建议等待时长与固定原因码；由协调器执行预算裁剪、计时和状态转换。P2 只交付规则实现，不引入额外模型客户端、复杂策略平台或后台轮询。
2. 策略输入与令牌分离，只含必要的业务快照：有序消息内容、接收间隔、批次状态和剩余时间等；以后可扩展近期上下文与会话节奏。replyToken、密钥、原始鉴权请求不得进入模型提示词。
3. 后续模型策略可建议 REPLY_NOW、WAIT_FOR_MORE、DELAY_REPLY，并返回受限的 wait_ms 和固定 reason_code；这些仅为设计示意，实际接口届时确认。P2 仍只有规则等待，模型能力不能标成已实现。

## 8.3 后续模型策略的执行约束

1. 模型提出建议，程序掌握最终调度权。建议必须通过枚举、数值范围、状态和剩余预算校验，不能延后批次硬截止时间、绕过删除屏障或复用已消费令牌。异常、超时、无效结果回退到确定性规则。
2. 策略调用本身耗时和费用也计入本轮总预算；限制每批次判断次数和并发，不对每条碎片输入持续重调模型。数据版本变化时丢弃过期判断；评估额外策略调用与在生成调用中附带时机建议的收益后再选实现。
3. 用户明确催促、明确要求稍等、连续补充、话题结束等作为评估场景，不仅按标点判断。模型拒绝及时回应或连续要求等待时也受硬上限约束；不把用户消息中的指令当作修改调度权限的系统指令。
4. 超过即时 Reply 窗口的数分钟等待、主动续聊或恢复发送，需要另行设计 Push 权限/额度、可持久化业务任务、取消机制和产品约定；任务中仍不得保存 Reply Token。当前只用 Reply 的授权不自动扩展到 Push。
5. 在授权的对话样本上评估提前打断率、用户补充后重生成率、等待时间分布、重复回复率、放弃率、调用成本和主观自然度。以改善交流为验收目标，不以让用户误认是真人为指标。具体策略模型、参数、评估阈值与是否支持结束话题后不回复，在后续阶段另行确定。
